# Интеграция LEGALIC

Календарь работает с LEGALIC через курсорный контракт `/sync/v1` — тот же, что
и LawMatic B2 (`Packages/LegalicSync`). Описание контракта на стороне сервера:
`legalic-site/docs/sync-api/endpoints.md`.

## Вход

- `POST /token`, тело `application/x-www-form-urlencoded`,
  `grant_type=password&login=<почта>&password=<пароль>`; продление —
  `grant_type=refresh_token`. Access-токен живёт сутки, refresh — 30 суток.
- `GET /sync/v1/me/info` — кем сервер нас видит (`guid`, `full_name`).
- Адрес сервера и почта хранятся в `UserDefaults` (это не секреты); пароль — в
  Keychain (`com.lawmatic.calendar.legalic` / `legalic.password`) и только после
  того, как сервер подтвердил пару. Токены живут в памяти `LegalicAPIClient`.
- Прежние ключи интеграции (`api_key`/`api_secret`) и настройки старого
  `/api/v1/task` удаляются при первом запуске (`removeLegacyCredentials`).

Код: `Shared/LegalicAPIClient.swift` (транспорт), `Shared/LegalicTaskMapper.swift`
(разбор записей и тело для записи), `Shared/Providers/LegalicProvider.swift`
(провайдер), `LawMaticCalendar/LegalicSettingsPane.swift` (настройки).

## Чтение

Два календаря:

| Календарь | Лента | Запись |
|---|---|---|
| «LEGALIC · Задачи» | `GET /sync/v1/task?cursor=…&limit=500` | да, если включено в настройках |
| «LEGALIC · Сроки по делам» | `GET /sync/v1/deadline?cursor=…&limit=500` | нет |

- Курсор ленты — это и `pageToken` внутри одного прогона, и `syncToken` между
  прогонами (`CalendarItem.syncToken`). Первый прогон читает ленту с начала до
  `has_more: false` (это `fullSnapshot`: локальные записи, которых нет в ленте,
  удаляются), дальше — только изменения по курсору.
- Испорченный курсор сервер отвечает `400` → `ProviderError.syncTokenExpired` →
  лента перечитывается с начала.
- `is_deleted: true` и `revoked[]` (отзыв доступа) → удаление локальной записи.
- Задача без единой даты (`start`, `finish`, `left/right_task_boundary`) — не
  событие календаря и не импортируется. Правила интервала: `displayRange(for:)`.
- Горизонт истории (настройка «Показывать задачи за»: 3 месяца / год /
  3 года / всё, по умолчанию год): записи, закончившиеся раньше, не
  импортируются, в том числе из инкрементов. Смена горизонта, смена правил
  отбора (`feedRulesVersion`) или кнопка «Перечитать заново» выставляют
  `requiresFullResync`, и координатор сбрасывает курсоры.
- Даты `Y-m-d H:i:s` без зоны трактуются в текущей зоне устройства. «Нулевые»
  даты (`0000-00-00`, год −1, `1899-12-30`) и всё вне 1970…2200 считаются
  отсутствием даты (`plausibleDateRange`): один такой импорт делал `events.json`
  нечитаемым для `JSONDecoder`. Хранилище теперь читает даты терпимо, а
  нечитаемый файл откладывает копией `*.broken-<дата>.json`, а не затирает.

Замер на `dev.legalic.ru` (16.09.2026): 40 897 задач с датами прочитаны
примерно за две минуты; после горизонта в календаре остаются только недавние.

## Запись задач

Выключена по умолчанию (`allowsWriteBack`): календарь — окно в рабочую базу.
Когда включена, календарь «Задачи» становится writable:

- создание — `POST /sync/v1/task` с клиентским `guid` (строчный UUID события),
  без `base_usn`; повтор после обрыва защищён заголовком `Idempotency-Key`
  (`<guid>-<localUpdatedAt>`);
- правка — тот же `POST` с `base_usn` = `usn` последней виденной версии
  (`CalendarEvent.externalETag`); `409` — расхождение версий →
  `ProviderError.preconditionFailed`, локальная правка остаётся в очереди, а
  следующий pull приносит серверную версию и LWW решает;
- удаление — `POST` с `is_deleted: true` и `base_usn`.

Поля: `caption` ← название, `message` ← заметки, `location`, `start`/`finish`
в формате сервера; целодневное событие — `00:00:00`…`23:59:59`.
Сроки по делам пересчитывает движок процесса, поэтому они только читаются.

## Ограничения

- Лента не фильтруется по датам на сервере, отсев — на клиенте.
- Полный прогон накапливает все страницы в памяти и сохраняет одним merge;
  обрыв на середине означает повтор с начала при следующем запуске.
- Участники задачи (`task_persons`), поручения и вложенные `gtd_events` не
  используются.
