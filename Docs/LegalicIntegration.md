# Интеграция LEGALIC

## Текущее поведение

- Авторизация: OAuth2 `client_credentials`, `POST {baseURL}/token`.
- Загрузка: `GET {baseURL}/{tasksListPath}`, по умолчанию `api/v1/task`.
- Пагинация: `page` / `per_page`, максимум страниц задаётся пользователем.
- API Key и API Secret хранятся в Keychain.
- Задачи маппятся в типизированные `ParsedRemoteEvent` и точечно обновляются по `guid`.
- LEGALIC отображается отдельным read-only календарём.

Старое поведение «удалить календарь и вставить всё заново» удалено. Автопереход календаря к первой импортированной дате также удалён.

## Почему нет write-back

В репозитории описаны только token endpoint и чтение списка задач. Нет подтверждённых методов:

- создать задачу;
- изменить задачу;
- удалить задачу;
- получить надёжную инкрементальную дельту или tombstones.

Поэтому `LegalicProvider.pushUpsert` и `pushDelete` явно возвращают `notImplemented`, а календарь имеет `isWritable = false`. Добавлять предполагаемые URL без контракта сервера нельзя: это создаст риск потери юридических данных.

## Ограничения чтения

- Сервер может содержать десятки тысяч задач.
- Проверенные `from` / `to` не гарантировали фильтрацию.
- Ответ может быть ограничен первыми N страницами.
- Поэтому клиент применяет полученные upserts, но не считает отсутствующую задачу удалённой.
- Строковые даты без timezone интерпретируются в текущей timezone устройства.

Для полноценной двусторонней синхронизации backend LEGALIC должен предоставить документированный CRUD, `updated_at`, удалённые записи/tombstones и cursor либо monotonically increasing revision.

Общая архитектура и настройка других провайдеров: [CalendarSync.md](./CalendarSync.md).
