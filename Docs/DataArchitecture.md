# Data Architecture

## Выбранный вариант

Для `LawMaticCalendar` выбран путь `local-first`:

- локальное хранилище в приложении является основой и работает офлайн;
- внешние интеграции подключаются как отдельные sync-коннекторы;
- при появлении своего backend сервер становится слоем синхронизации и совместной работы, но не убирает локальный кэш.

На текущем этапе в коде уже реализован baseline на локальном файловом storage. Это даёт предсказуемый запуск, сохранение после перезапуска и простую отладку без внешней инфраструктуры.

## Почему не только локальный JSON

JSON-файлы подходят как ближайший production-baseline для текущего MVP:

- просто внедряются;
- легко отлаживаются;
- не требуют миграций на старте;
- хорошо подходят для одного пользователя и небольшого объёма данных.

Но это промежуточный шаг. Если в приложении появятся:

- поиск по большому числу событий;
- сложные фильтры;
- вложенные связи;
- конфликтное редактирование;

то следующий шаг должен быть в сторону локальной базы данных, а не дальнейшего роста файлового слоя.

## Варианты хранения данных

### 1. Своя локальная база

Подход:

- приложение хранит данные полностью локально;
- источник истины находится на устройстве;
- сеть не обязательна.

Технологические варианты:

- `SQLite` или `SQLite.swift` для контролируемой схемы и миграций;
- `SwiftData` для более нативной интеграции с Apple-экосистемой, если проект останется полностью на платформах Apple;
- `Core Data`, если нужна зрелая объектная модель и мощные инструменты миграций.

Плюсы:

- лучший офлайн-режим;
- минимальная зависимость от внешних сервисов;
- низкая стоимость поддержки на раннем этапе;
- быстрый отклик UI.

Минусы:

- нет синхронизации между устройствами без дополнительного слоя;
- сложнее сделать совместную работу;
- резервное копирование и перенос данных надо продумывать отдельно.

Когда подходит:

- один пользователь;
- desktop-first сценарий;
- MVP и ранний production;
- важен офлайн.

Рекомендация для этого проекта:

- это лучший следующий этап после текущего файлового storage;
- если приложение пойдёт в прод и начнёт расти, стоит мигрировать local storage в `SQLite.swift`.

### 2. Своё API и база на сервере

Подход:

- сервер становится главным источником истины;
- клиент получает данные через API;
- локально хранится кэш и очередь изменений.

Плюсы:

- синхронизация между устройствами;
- единая бизнес-логика;
- совместная работа, права доступа, аудит;
- проще интегрировать веб-клиент и мобильные клиенты.

Минусы:

- самая высокая стоимость разработки и поддержки;
- нужен backend, auth, миграции, мониторинг, бэкапы;
- без локального кэша UX офлайна заметно хуже;
- возникает тема конфликтов синхронизации.

Когда подходит:

- нужен multi-device;
- нужен общий календарь команды;
- данные должны жить в вашей системе;
- есть планы на SaaS или кабинет пользователя.

Рекомендация для этого проекта:

- делать после стабилизации локального слоя;
- сервер не должен заменять локальный кэш, лучше строить `local-first + sync`.

### 3. Интеграция с Google Calendar

Подход:

- события читаются и записываются через Google Calendar API;
- пользователь авторизуется через OAuth;
- Google становится внешним провайдером календаря.

Плюсы:

- готовая инфраструктура календарей;
- синхронизация между устройствами уже существует;
- знакомый пользователю источник данных;
- удобно для рабочих аккаунтов Google Workspace.

Минусы:

- OAuth, refresh token, rate limits;
- зависимость от внешнего API и его квот;
- не все ваши продуктовые сценарии могут укладываться в модель Google Calendar;
- сложнее поддерживать уникальные локальные функции.

Когда подходит:

- продукт должен быть в первую очередь клиентом к Google Calendar;
- целевая аудитория уже живёт в Google Workspace;
- своя серверная модель не нужна на старте.

Рекомендация для этого проекта:

- подключать как внешний источник календарей, а не как единственный storage;
- хранить локальный кэш событий и метаданные синхронизации.

### 4. Интеграция с Apple Calendar

Подход:

- доступ через `EventKit` к локальным/системным календарям Apple;
- приложение работает как клиент к уже существующей календарной базе пользователя.

Плюсы:

- лучшая интеграция на macOS;
- системные разрешения и привычный UX;
- доступ к iCloud-календарям и локальным календарям пользователя;
- меньше инфраструктуры, чем в варианте со своим API.

Минусы:

- сильная привязка к Apple-экосистеме;
- меньше контроля над схемой данных;
- некоторые продуктовые функции ограничены возможностями `EventKit`;
- сложнее строить кроссплатформенный продукт вокруг этого как единственного источника истины.

Когда подходит:

- приложение позиционируется как macOS-клиент;
- основная аудитория использует системный календарь Apple;
- вы не хотите сразу строить backend.

Рекомендация для этого проекта:

- очень хороший кандидат на первую внешнюю интеграцию для macOS-версии;
- лучше делать как адаптер поверх локального слоя и модели синхронизации.

### 5. Что ещё можно рассмотреть

#### CalDAV

Подходит для Nextcloud, Fastmail и других провайдеров, где есть открытый календарный протокол.

Плюсы:

- меньше vendor lock-in;
- работает не только с Google/Apple;
- хорошо для B2B и self-hosted сценариев.

Минусы:

- протокол и реализация сложнее;
- много вариативности между провайдерами.

#### Microsoft Graph / Outlook Calendar

Если аудитория корпоративная, этот вариант часто не менее важен, чем Google.

Плюсы:

- корпоративный рынок;
- интеграция с Microsoft 365.

Минусы:

- OAuth и политика прав доступа;
- отдельная интеграция и отдельные edge cases.

#### CloudKit

Хорош для Apple-only сценария, если нужна синхронизация между устройствами без своего backend.

Плюсы:

- меньше серверной инфраструктуры;
- нативная интеграция в Apple-экосистеме.

Минусы:

- сильная привязка к Apple;
- хуже подходит, если дальше нужен веб или Android.

## Практический выбор для проекта

### Сейчас

- оставить `local-first`;
- текущий файловый storage использовать как ближайший production-baseline;
- довести тесты, миграцию состояния и стабильность UI.

### Следующий шаг

- перейти с JSON-файлов на `SQLite.swift`, если объём логики и данных вырастет;
- оставить тот же интерфейс store/repository, чтобы UI не зависел от конкретного способа хранения.

### Потом, если нужен рост продукта

- добавить своё API для аккаунтов, командных календарей и multi-device;
- Google Calendar и Apple Calendar подключать как внешние провайдеры синхронизации;
- не строить архитектуру, где весь продукт зависит только от одного внешнего календарного API.

## Внешние календари

Google Calendar и Apple Calendar реализованы как двусторонние коннекторы поверх общего LWW sync-engine. LEGALIC подключён через тот же контракт, но остаётся read-only до появления документированного CRUD API. Детали: [CalendarSync.md](./CalendarSync.md) и [LegalicIntegration.md](./LegalicIntegration.md).

## Итоговая рекомендация

Для `LawMaticCalendar` наиболее здоровая траектория такая:

1. `local-first` как основа.
2. `SQLite.swift` как следующий локальный storage, когда MVP подтвердится.
3. Свой backend только когда появится реальная потребность в multi-device, совместной работе и серверных правилах.
4. Google Calendar, Apple Calendar, CalDAV и Outlook подключать как коннекторы, а не как единственную модель данных продукта.
