# Интеграция LEGALIC (состояние на этапе теста)

Документ фиксирует, что уже сделано в коде, какие ограничения у API и клиента, и что **намеренно временно** / подлежит переработке перед «нормальной» версией продукта.

## Что реализовано

### Аутентификация и запросы

- OAuth2 `client_credentials`: `POST {baseURL}/token` с `api_key`, `api_secret`.
- Кэш `access_token` в памяти процесса (`LegalicAPIClient`), срок из `expires_in`.
- Загрузка задач: `GET {baseURL}/{tasksListPath}` (по умолчанию `api/v1/task`), не `…/tasks`.

### Пагинация

- В query добавляются `page` и `per_page`; за один синк запрашивается до `min(page_count, taskSyncMaxPages)` страниц.
- Настройки в приложении: «Страниц за синк», «Задач на страницу» (`LegalicService`, форма настроек).
- Ответ разбирается как объект с полями `items`, `page`, `page_count`, `per_page`, `total_count`.
- Задачи с разных страниц объединяются с дедупликацией по `guid` (на случай пересечений).

### Разбор задач

- `LegalicTaskJSONParser`: поля `guid`, `caption`, `start` / `finish`, `created` / `updated`, `is_deleted`, вложенности и альтернативные ключи (запас под другие форматы ответа).
- Формат дат из API: `start` / `finish` — строки вида `yyyy-MM-dd HH:mm:ss` (без явной таймзоны в JSON); `created` / `updated` — Unix-секунды.

### Календарь приложения

- Отдельный календарь «LEGALIC» со стабильным UUID (`LegalicCalendarConfiguration`), события с `externalId` (guid) и `externalSource = "legalic"`.
- При синке: удаление прежних событий этого календаря (полная замена при выгрузке без фильтра по видимому периоду; иначе — удаление попавших в диапазон), затем запись новых.
- Если календарь был скрыт (`isVisible == false`), при синке показ снова включается (`ensureLegalicCalendarExists`).

### Фильтр по видимому периоду (опционально)

- Тоггл «Только видимый период календаря»: к URL добавляются query-параметры `from` / `to` (имена настраиваются), значения в ISO 8601.
- **Важно:** на стороне `legalic.ru` в проверенных запросах эти параметры **не сужали** выборку: первая страница оставалась «с начала базы» (2018 и т.д.). Это ограничение/особенность API или неверные имена параметров — см. раздел «Ограничения».

## Ограничения (текущие)

1. **Объём данных:** полная база задач — десятки тысяч записей и тысячи страниц при `per_page=50`. Текущий синк сознательно ограничен числом страниц в настройках.
2. **Сортировка API:** первые страницы отдают **старые** задачи (например, 2018). Без рабочего серверного фильтра по датам пользователь не увидит «сегодняшние» задачи, пока не пролистает соответствующие страницы или не появится другой endpoint/параметры.
3. **Фильтр `from`/`to`:** по факту тестов из терминала и приложения не подтверждено, что диапазон применяется; нужна сверка с документацией LEGALIC / LawMatic B2.
4. **Таймзона строк `start`:** строка без `Z` разбирается через `DateFormatter` с `TimeZone.current` и вариантами — возможны сдвиги при смене часового пояса или если сервер подразумевает фиксированную зону (например, только Москва).
5. **Нет инкрементального синка:** каждый полный режим перезаписывает весь календарь LEGALIC локально; нет `updated_since`, курсоров, etag.
6. **Нет лимитов и бэкоффа:** при большом `taskSyncMaxPages` возможны долгие серии запросов подряд.

## Технический долг и что переделать

### 1. Принудительный переход даты календаря после синка — **временная мера для теста**

**Где:** `CalendarViewModel.focusCalendarOnLegalicImportsIfNeeded`, вызывается после импорта.

**Поведение:** если ни одна из импортированных задач не пересекает **текущий** видимый диапазон (день/неделя/месяц/год), `selectedDate` сдвигается на начало суток **самой ранней** задачи в партии (чтобы было видно, что импорт сработал).

**Почему это не для продукта:** в нормальном приложении нельзя без согласия пользователя «прыгать» на 2018 год; ломается контекст (пользователь смотрел март 2026), возможны сюрпризы при фоновом синке.

**Как сделать правильно (варианты):**

- убрать автосдвиг полностью и вместо этого показывать **ненавязчивое уведомление**: «Импортировано N задач; в выбранном периоде их нет. [Перейти к первой дате] [Закрыть]»;
- или отдельный экран/список «Задачи LEGALIC» с сортировкой и переходом в календарь по тапу;
- или автосдвиг только если пользователь явно включил опцию в настройках («После синка показывать первую импортированную дату»).

**Действие:** пометить в коде `TODO`/комментарием и удалить или заменить, как только будет UX-решение.

### 2. Дефолт «Только видимый период»

Сейчас для **новых** установок по умолчанию выключено (`syncTasksInVisibleRangeOnly = false`), потому что `from`/`to` на проверенном API не работали как фильтр. После появления рабочего фильтра на сервере имеет смысл пересмотреть дефолт и тексты в настройках.

### 3. Модель синка

- Разделить «полная перезагрузка» и «догрузка страниц / инкремент».
- При полной перезагрузке сохранять стабильность `externalId` и решить, нужны ли локальные правки событий LEGALIC (сейчас перезапись затрёт их).

### 4. Производительность и хранилище

- При росте числа событий файловый JSON может стать узким местом — см. общий план в `DataArchitecture.md` (SQLite и т.д.).
- Для больших импортов — фоновая очередь, прогресс, отмена.

### 5. Безопасность

- API Secret не логировать; ключи только в Keychain в перспективе, не только UserDefaults.

### 6. Тесты

- Юнит-тесты на парсер (примеры реального JSON: строковые даты, `null` finish, `is_deleted`).
- Моки HTTP для клиента (токен, две страницы пагинации, 401 и обновление токена).
